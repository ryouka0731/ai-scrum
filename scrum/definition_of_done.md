# 完成の定義（Definition of Done）

> 完成の定義は、インクリメントがプロダクトに必要な品質基準を満たした状態を正式に記述したものである。
> プロダクトバックログアイテムが完成の定義を満たした瞬間にインクリメントが誕生する。
> — スクラムガイド 2020

## 対象プロダクト

社内タスク管理Webアプリ（TaskLite） / SvelteKit（SPA）+ Node.js API + SQLite（ローカル環境）

## 完成の定義

すべての項目が「はい」と判定できた場合に、そのプロダクトバックログアイテムは「完成」とみなす。

---

### 1. コード品質

| # | 基準 | 判定 |
|---|------|------|
| 1-1 | フォーマッタ・リンタ（Prettier / ESLint）を実行し、エラー・警告なく通過する | はい / いいえ |
| 1-2 | 型チェックを含むビルド（`npm run build` / `svelte-check` 等）がエラーなく完了する | はい / いいえ |
| 1-3 | デバッグ用の `console.log` ・コメントアウトされた不要コード・未使用の import が残っていない | はい / いいえ |

### 2. テスト

| # | 基準 | 判定 |
|---|------|------|
| 2-1 | 対象PBIの受入基準に対応する自動テスト（API の正常系・異常系のユニット/結合テスト）が存在する | はい / いいえ |
| 2-2 | テストを一括実行するコマンド（`npm test` 等）が用意され、失敗テストが0件で完了する | はい / いいえ |
| 2-3 | 想定外入力（必須欠落・不正な型・不正な状態値など）に対する異常系テストが少なくとも1件含まれる | はい / いいえ |

### 3. ドキュメント

| # | 基準 | 判定 |
|---|------|------|
| 3-1 | ローカルでの起動手順（依存インストール・起動コマンド）が README 等に記載されている | はい / いいえ |
| 3-2 | 実装したPBIの内容と使い方が、利用者が読んで理解できる形で記載されている | はい / いいえ |

### 4. 動作確認

| # | 基準 | 判定 |
|---|------|------|
| 4-1 | ローカル環境でアプリが起動し、対象PBIの主要操作を画面上で一通り実行できる | はい / いいえ |
| 4-2 | 対象PBIの受入基準の各項目を実際の操作で「はい」と確認できる | はい / いいえ |
| 4-3 | 想定外の入力（未入力・不正な値など）でアプリが停止せず、利用者に分かる形で扱われる | はい / いいえ |

### 5. セキュリティ

| # | 基準 | 判定 |
|---|------|------|
| 5-1 | API への入力値をサーバ側で検証し、必須欠落・不正な型・許可外の状態値を 400 系で拒否する | はい / いいえ |
| 5-2 | DB アクセスはパラメータ化クエリ（プレースホルダ）を用い、ユーザー入力を SQL 文字列に連結していない | はい / いいえ |
| 5-3 | ユーザー入力を画面表示する際、SvelteKit 既定のエスケープにより XSS が発生しない（`{@html}` を無検証で使っていない） | はい / いいえ |
| 5-4 | `npm audit` を実行し、依存パッケージに high 以上の未対応脆弱性が残っていない | はい / いいえ |

### 6. パフォーマンス

| # | 基準 | 判定 |
|---|------|------|
| 6-1 | タスク一覧 API はローカル環境で100件程度のデータに対し体感1秒以内に応答する | はい / いいえ |
| 6-2 | 一覧の並べ替え・絞り込みは DB クエリ（ORDER BY / WHERE）で行い、全件取得後のクライアント側処理に依存していない | はい / いいえ |

### 7. UI/UX の品質

| # | 基準 | 判定 |
|---|------|------|
| 7-1 | 主要な操作（登録・状態変更・並べ替え・絞り込み）の導線が画面上で明確に分かる | はい / いいえ |
| 7-2 | 操作の結果（登録完了・状態変更・絞り込み中など）が利用者に視覚的に伝わる | はい / いいえ |
| 7-3 | タスクが0件・絞り込み結果が0件のときに、空であることが分かる表示になっている | はい / いいえ |

### 8. データベース

| # | 基準 | 判定 |
|---|------|------|
| 8-1 | SQLite のスキーマ（テーブル定義）が初期化/マイグレーションスクリプトとしてコード管理され、初回起動時に自動作成される | はい / いいえ |
| 8-2 | アプリ・サーバを再起動してもタスクデータが永続化され保持される | はい / いいえ |
| 8-3 | 主キー・NOT NULL・状態値の制約など、データ整合性を守る制約がスキーマに設定されている | はい / いいえ |

### 9. 仕様準拠

| # | 基準 | 判定 |
|---|------|------|
| 9-1 | 実装は対応する仕様書（`scrum/sprintXXX/specs/PBI-XXX.md`, status: active）の受入基準をすべて満たしている | はい / いいえ |
| 9-2 | 実装は仕様書のインターフェース（画面・API・データ構造）と一致している | はい / いいえ |
| 9-3 | 仕様書の Non-goals に反するスコープ外の作り込みがない | はい / いいえ |

---

## 補足事項

- 本DoDのうち技術（コード品質・テスト・セキュリティ・パフォーマンス・データベース・仕様準拠の詳細）に関する基準は、後工程で開発者が具体化する。
- ビジネス観点（ドキュメント・動作確認・UI/UX）の基準は鈴木（PO）がリファインメントで設定した。
